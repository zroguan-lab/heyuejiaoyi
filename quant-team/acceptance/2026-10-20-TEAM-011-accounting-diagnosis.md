# TEAM-011 四笔等待成交账务诊断

结论：**FAIL（当前执行状态机存在已复现的事实冲突处理缺口）；四个目标标的在本次时点的持仓/残单风险检查 PASS；全账户风险未据此宣告 PASS；盈利与亏损结果 UNKNOWN。**

取证时间：2026-10-20 约 01:00–01:07（北京时间）。本轮仅使用活动库只读事务与 Binance Demo 签名 GET；没有下单、撤单、平仓、修改活动库、策略、配置或服务。

## 交易所只读事实

四笔均得到相同结果：

- 按本地 `orderId` 查询订单：HTTP 400 / Binance `-2013`（订单不存在）。
- 按本地 `clientOrderId` 查询订单：同为 `-2013`。
- 按精确 `orderId` 查询 `userTrades`：空。
- 查询入场前 5 分钟至后 30 分钟的同币 `userTrades`：空；未发现被错误绑定到其他订单 ID 的成交。
- 本地计划中的 stop / break-even `clientAlgoId`：均为 `-2013`。
- 当前同币持仓、普通挂单、条件挂单：均为空。
- 从 run 创建前 1 分钟至本次取证的 Funding：均为空。

当前凭据指纹与活动库保存的权限验证指纹一致；权限验证记录时间晚于四笔 run，因此它支持“当前诊断与当前服务使用同一凭据”，但不能单独证明每笔提交瞬间没有外部环境变量覆盖。`.env` 文件修改时间早于四笔记录且未变，进一步降低凭据切换可能性，不能将其降为绝对零。

## 本地事实

- 四笔 `entryOrder.status=FILLED` 且 `executedQuantity>0`。
- 四笔 `result.trades=[]`，严格归属订单只有入场 ID，没有退出 ID。
- 没有 `POSITION_PROTECTED`、`POSITION_RECONCILED`、保护建立或平仓成功审计。
- 首次 `ACCOUNTING_PENDING` 在本地 `ENTRY_ORDER_CONFIRMED` 后约 2–9 秒出现，并持续重试数百次。
- 现行账务条件要求入场与退出 ID 均非空且全部有成交；四笔退出 ID 为零，现有循环无法自行完成。

## 根因

### 已证实的状态机缺口

执行器在下单响应返回 `FILLED` 时，立即把 run 推进为 `PROTECTION_PENDING`。随后 `reconcileProtected()` 若看不到仓位，就直接进入残单清理与账务收集；它没有先验证：

1. 入场订单能否被签名 GET 重新查询；
2. 是否存在严格归属的入场成交；
3. `FILLED` 响应与账户无仓位之间是否构成提交事实冲突。

因此，“本地 FILLED、当前交易所查询无法印证、且账户无仓位”的记录被错误归类为普通 `ACCOUNTING_PENDING`，并因缺退出 ID 永久重试。应将其归类为 `LOCAL_ENTRY_ACK_UNVERIFIABLE` / `ENTRY_FACT_CONFLICT` 一类的事实冲突；不能仅凭当前查询命名为“从未持久化”。

### 仍未知

- Binance Demo 为什么在提交响应阶段产生了本地 `FILLED` 记录、之后却无法查询；当前没有保存原始脱敏响应哈希或每-run账户指纹，不能进一步区分 Demo 临时异常、代理响应异常或运行时账户上下文变化。
- 四笔没有交易所成交证据，不能计算盈利或亏损，也不能把本地零值当实际零盈亏。

## 影响

- 四笔不应进入胜率、PF、NetR 或净盈亏统计。
- run 仍被视为活动执行，会阻挡同标的后续交易。
- 对账循环不断写入重复审计，造成噪声与库增长。
- 当前无对应仓位和残单，未发现这四笔带来的实时敞口；这不等于整个账户没有其他持仓。
- `ACCOUNTING_PENDING` 本身不触发全局安全锁，所以不是全系统停止下单的直接原因。

## 建议修复（不改变交易策略）

### P0：入场事实确认

1. 下单响应 `FILLED` 只作为 ACK，不直接视为完整成交事实。
2. 进入保护生命周期前，使用相同 `clientOrderId` 重查订单，并核验成交数量；允许交易所明细短暂延迟。
3. 若账户已有仓位但 fills 延迟，先保护仓位，再保持账务待核，不能为了等账让仓位裸奔。
4. 若订单、成交、仓位、挂单均持续无法印证，进入专门的事实冲突状态，例如 `ENTRY_FACT_CONFLICT`；只有在提交时账户指纹、响应血缘与历史可见性足以证明时，才能细分为 `ENTRY_ACK_NOT_PERSISTED`。该类记录 `performanceEligible=false`、净盈亏保持未知，不得进入普通 `ACCOUNTING_PENDING`。
5. 每个 run 保存账户凭据指纹、请求证据摘要和响应内容哈希，不保存密钥或签名。

### P1：账务完整性

- `ACCOUNTING_PENDING` 仅用于“至少一笔真实入场成交已确认，但退出/Funding/费用仍不完整”。
- 退出 ID 只纳入实际成交订单；null、空串、数字 `0`、字符串 `"0"` 和未成交取消腿不得成为必需成交 ID。
- `userTrades` 做可证明完整的分页、去重和数量闭合；到达 1000 条上限不能宣布完整。
- 手续费、realizedPnl 缺失不得补零后判完整；Funding 查询失败不得当零。
- `accountingComplete!==true` 时，前端及投影层的确认净盈亏、NetR 必须保持 null。

### P2：历史四笔恢复

- 不覆盖或删除原始 payload、审计和快照。
- 另行受控部署后，追加带来源和取证时间的对账证据。
- 只有再次确认无持仓、无普通/条件单、无订单及成交后，才可将四笔转为终态执行异常并释放同币门控。
- 不补造退出 ID，不把四笔记为盈利、亏损或零收益。

## 独立验收重点

- `FILLED` ACK + 订单/fills/仓位暂时不可见：先重试，不能立刻关闭或结算。
- `FILLED` ACK + 仓位存在但 fills 延迟：保护优先，账务仍未知。
- `FILLED` ACK + 多次权威查询均无法印证：事实冲突隔离、无绩效；证据不足时不宣称当时未下单。
- 真实入场成交存在但退出身份缺失：继续隔离，不能为解锁伪造 CLOSED。
- 取消腿 `actualOrderId="0"` 不阻塞结算。
- 分页、重复 fill、部分成交、费用缺失、Funding 失败均有反例测试。
- 修复离线通过不等于部署通过；部署需备份、单实例交接及上线后只读复核。

## 专家讨论摘要

- 执行专家：现有客户端可安全复用，但 `writeEnabled=false` 仍允许测试订单端点，所以本次在 fetch 传输层额外硬拒绝所有非 GET。
- 运行可靠性：原页面/健康接口只提供缓存，不能替代指定订单历史查询；启用项目相同代理后签名 GET 成功。
- 独立审查：`actualOrderId="0"` 是另一项真实反例，但不是这四笔共同原因；四笔共同原因是没有任何退出身份且真实入场事实也无法确认。
- 独立审查反方意见：当前凭据指纹只绑定较晚的权限验证，不能证明提交瞬间必为同一账户；总控接受该限制，并将结论从“未持久化”下调为“本地 ACK 与当前权威查询冲突”。
- 反方边界：释放同币门控可能合理，但必须同时保留持续对账与不可变证据，不能只把状态改成 CLOSED/CANCELED。
