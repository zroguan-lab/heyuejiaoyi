# V2.3 历史数据目录

状态：M2历史数据基础设施已完成；M6逐时点全市场快照与排名分批回填已接入（2026-10-04）。

## 目标和边界

这层只负责保存可审计的历史市场事实，不生成信号、不读取Demo API密钥，也不提交、修改或撤销订单。它与实时交易数据库 `data/research.sqlite` 分离，默认写入被Git忽略的 `research-data/`。

权威关系如下：

```text
Binance生产公共只读行情
  -> 1m K线 / Funding / exchangeInfo / 全市场成交额与盘口快照
  -> K线/Funding/合约按UTC月分区；高频全市场事实按UTC小时分区
  -> SHA-256内容寻址压缩对象（不可变）
  -> manifest当前修订与历史修订
  -> 完整性及缺口审计
  -> M3逐时点Top100/Movers重建
```

历史目录不能成为Demo账户或订单状态的来源；Demo执行仍以Binance Demo账户和执行状态机为权威来源。

## 保存内容

| 数据 | 粒度 | 用途 |
| --- | --- | --- |
| K线 | 原始1分钟 | 派生5m/15m/1h、逐分钟成交路径、历史涨跌幅与量能排名 |
| Funding | 交易所事件时间 | 回放持仓成本 |
| 合约元数据 | 每次同步快照 | 上市时间、状态、精度和过滤器审计 |
| 全市场快照 | 每次采集时点 | 当时合格合约、24小时成交额排名、买一卖一、点差与Top100覆盖证明 |

更高周期不重复下载，后续从1分钟原始事实确定性派生，避免多个周期来源不一致。

## 目录结构

```text
research-data/
  manifest.json
  objects/
    sha256/
      ab/
        <完整SHA-256>.jsonl.gz
```

对象文件写入后不覆盖。同一月分区有新增记录时，会生成新对象和新修订；manifest只移动“当前修订”指针，并保留旧修订信息。对象哈希基于规范化、未压缩的NDJSON内容，因此压缩实现变化不会改变数据身份。

目录使用独占写锁和进程内写队列，避免并发同步互相覆盖manifest。异常退出留下写锁时会明确报错并要求人工核实，不会自动猜测锁是否可以删除。

长时间回填使用有限时长的写锁等待，因此不会因为5分钟事实采集器正在写一个小分区，就把已经下载完成的单币数据全部丢弃；事实采集器本身仍采用快速失败并在下一周期重试。

## 使用

同步最近1天BTC：

```powershell
npm run data:sync -- BTCUSDT 1
```

同步最近30天三个标的：

```powershell
npm run data:sync -- BTCUSDT,ETHUSDT,SOLUSDT 30
```

只积累一份当前全市场逐时点快照，不下载K线：

```powershell
npm run data:snapshot
```

按已封存流动性排名分批同步。例如同步Top10最近1天；最后一个参数是排名偏移量：

```powershell
npm run data:sync-top -- 10 1 0
```

首批输出会包含 `selectionSnapshot.capturedAt`。所有后续批次必须把这个值作为第6个参数传回，确保整个批次族使用同一榜单事实与同一分钟时间窗：

```powershell
npm run data:sync-top -- 10 1 10 <snapshotCapturedAt>
```

偏移量大于0但未提供该值时，命令会主动失败，避免各批次看似完整、实际却无法在同一决策时点联合回放。

单批最多50个标的。`sync-top`的币种选择来自写入目录的快照，不在下载途中重新排序，因此可以审计“当时为什么选了这些币”。

Top100长窗口使用带检查点的可恢复任务。任务固定首份榜单和时间窗，每个标的开始前都以目录实际覆盖重新判断，检查点只显示进度、不是数据完成的权威来源：

```powershell
npm run data:backfill-universe -- --snapshot=<snapshotCapturedAt> --days=180 --count=100 --max-symbols=1
```

去掉 `--max-symbols=1` 或改为100即可继续同一检查点。默认检查点为 `research-data/backfill-top100-180d.json`；重复运行会跳过目录中已经完整的标的。上市不足窗口长度的币只从真实上市时间开始保存，并明确标记 `listingLimited`，不会伪造上市前K线。

历史客户端默认把分页请求限制为每500毫秒一次，并在Binance返回429/418时遵守本地暂停时间后有限重试。该节流只作用于历史回填，不改变实时扫描或Demo执行客户端。

180天主回填完成后，使用独立追平任务把同一批Top100分钟K线延伸到最新已封存全市场快照。追平任务不重新选币，并与主回填共用单一作业锁；主回填未完成时会拒绝启动：

```powershell
npm run data:catchup-universe
```

默认检查点为 `research-data/catchup-top100.json`。每次运行固定一个目标快照，逐币先审计原180天基线，再追加K线和Funding；中断可续跑。上一次追平完成且出现更新快照时，会开启新一轮固定目标并保留最近的运行摘要。追平检查点仍只是进度投影，manifest和内容对象才是数据权威来源。

若主回填仍在运行，可启动自动接棒器：

```bash
npm run data:continue-pipeline
```

它等待主回填达到100%且零失败后，依次执行分钟追平、严格单点重放和20点严格验证；不会打开封存样本，也不会接触Demo交易服务。运行状态写入 `research-data/historical-pipeline-status.json`。

离线审计已有目录：

```powershell
npm run data:audit
```

同步命令只允许 `https://fapi.binance.com`，每次最多50个交易对、1–180天。扩大到全市场时应分批执行并在每批后审计，避免网络中断造成无法定位的缺口。新版全市场快照同时保存买一、卖一与计算点差并校验三者一致；早期只有点差的不可变快照按旧版规范保留。全市场快照只能证明采集时点之后的市场事实，不能倒填或伪造过去的盘口与Top100成分。

## 审计规则

- SHA-256必须与解压后的规范化内容一致；
- 同一主键出现不同内容时拒绝合并；
- OHLC关系、成交量和收盘时间必须有效；
- 1分钟记录必须连续，内部、开头和结尾缺口分别记录；
- manifest对象路径必须留在历史目录内；
- 数据缺口可以被保存和报告，但不能被标记为完整。
- 全市场快照必须包含唯一标的、连续流动性排名、有效成交额和非负点差；任何字段不完整都会拒绝写入。

## M2验收与M3边界

M2基础设施的验收条件：

1. 数据目录与Demo SQLite、API密钥、交易端点隔离；
2. 原始对象不可变且可按哈希验证；
3. 分区更新保留历史修订；
4. 缺口、损坏和同时间冲突均能被自动测试发现；
5. 实际公共行情金丝雀同步后 `npm run data:audit` 为健康。

M2不等于V2.3回测完成。M3已经能重建历史雷达，M6开始积累逐时点全市场事实并按封存排名回填分钟数据。只有Top100共同历史达到180天、各验证时点都有不晚于决策时间的合约与点差快照，并通过M5闸门后，才能讨论历史晋级；当前结果仍不能宣称V2.3具有历史盈利能力。
